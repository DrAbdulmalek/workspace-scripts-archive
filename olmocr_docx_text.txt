Executive Summary
This report answers the owner stop-gate directive of 2026-09-16: perform an OLMoCR TECHNICAL + ARCHITECTURAL AUDIT only — no implementation, no merge, no push, no migration, no workflow creation. It also resolves the test-count contradiction (238 vs 114) recorded against the Phase-1 completion report; the full resolution with raw pytest evidence is in Annex A.
Classification answer (owner question 6): OLMoCR is Option E — a hybrid OCR + document-understanding component. It is not a classic OCR engine: the toolkit renders each PDF page to a 1288-px image, sends it to a 7-billion-parameter vision-language model (a fine-tune of Qwen2.5-VL-7B-Instruct, served through vLLM), and returns Markdown with a YAML front matter block; equations are emitted as LaTeX and tables as HTML. The pipeline layer adds rendering, work-queue batching, retry ladders, and a pdftotext last-resort fallback. Upstream is active: v0.4.27 released 2026-03-12; code Apache-2.0; model weights Apache-2.0.
The decisive negative finding concerns Arabic: the model card declares language: en only, the olmOCR-2 paper itself calls olmOCR-Bench an English-language benchmark, and the published training mix (olmOCR-mix-1025) is 91.3–99.8% English per subset with Arabic absent from every top-5 language list. Arabic capability is therefore classified UNPROVEN for every Arabic row of the capability matrix. The integration is architecturally clean — the exact integration points are the Phase-1 canonical adapter protocol, the benchmark wrapper family, and the packages/core registry/router — but a GO decision is conditional on an Arabic-inclusive benchmark that has not yet been run.

3. OLMoCR Exact Architecture (Upstream Audit)
3.1 What OLMoCR actually is
Owner question 6 offered five classifications. The evidence supports Option E: a hybrid OCR + document-understanding component — specifically a PDF-to-Markdown pipeline (option C) wrapped around a fine-tuned 7B vision-language model (option B/D characteristics), and not a conventional OCR engine (option A). Evidence: the upstream README describes “a toolkit for converting PDFs and other image-based document formats into clean, readable, plain text format” based on “a 7B parameter VLM, so it requires a GPU”; the HF config.json declares architectures: [Qwen2_5_VLForConditionalGeneration]
 with FP8 compressed-tensors quantization; the model card states it is fine-tuned from Qwen/Qwen2.5-VL-7B-Instruct
 on olmOCR-mix-1025 with additional GRPO reinforcement learning; and the olmOCR 2 paper (arXiv 2510.19817) describes training with reinforcement learning on verifiable binary unit tests. It recognizes no per-character boxes, exports no confidence scores, and does not segment words — all defining properties of the OCR engines already in this repository.
Consequently, owner framing matters downstream: inside this repository OLMoCR would enter as a document-understanding engine that produces structured Markdown for whole pages, complementary to — not competing with — Tesseract/PaddleOCR text OCR. The v4 production prompt (prompts.py:164-171, the one actually wired at pipeline.py:139) instructs: return plain text as read naturally, convert equations to LaTeX and tables to HTML, label figures as ![Alt](page_startx_starty_width_height.png)
, and emit a YAML front matter with primary_language, is_rotation_valid, rotation_correction, is_table and is_diagram. Notably the v4 prompt, unlike the older v1/v2 prompts, contains no handwriting instruction — handwriting support is therefore graded PARTIALLY PROVEN (historical claim) rather than PROVEN.

3.3 Page-boundary and document assembly behavior
For integration design it matters exactly how upstream assembles documents. build_dolma_document
 (pipeline.py:602-636) joins per-page natural_text
 values with a plain newline and records pdf_page_spans
 — [start_char, end_char, page_num] per page — in the Dolma JSON metadata, alongside Source-File, olmocr-version, pdf-total-pages and token totals. The markdown file written by --markdown is therefore a flat concatenation in which page boundaries are recoverable only via the spans, not visible in the .md itself (pipeline.py:765-794 writes doc[“text”]). Any adapter in this repository must keep those spans so per-page provenance survives — see section 5.

5. OCRResult Compatibility and Markdown Representation
Owner question 9 asks whether the current OCRResult needs a markdown
 field, whether Markdown fits existing structure, or whether a separate DocumentResult
 is required — without implementing anything. The canonical contract (contract/result.py:90
) carries: text, segments (tuple of Segment: text, confidence, bbox, language, extras), confidence, engine, language, metadata (open, additive-else map with a documented closed key set), preprocessing, fallback_chain, provenance, warnings, errors, contract_version. Its evolution policy declares additive optional fields or documented additive metadata keys to be MINOR changes; unknown top-level keys are a hard error in from_dict, but metadata keys are explicitly open.
Three options were analyzed against the information-preservation rule (nothing existing may be dropped; no silent loss):
Option 1 — metadata["markdown"] + page-level segments (RECOMMENDED first step): the validated OLMoCR Markdown is stored verbatim in metadata.markdown; per-page Segments carry each page’s markdown fragment with extras {page_num, char_start, char_end} mirroring upstream pdf_page_spans; metadata.olmocr_front_matter keeps primary_language/rotation/is_table/is_diagram. Zero code change to result.py (metadata is additive-else); one documented mapping row; contract_version stays 1.0.0 or moves to 1.1.0 per policy documentation.
Option 2 — named canonical field markdown: a typed, discoverable field; still only a MINOR bump (additive optional), but it edits the frozen dataclass, requires a full CONTRACT_FIELD_MAPPING decision row with information-preservation rationale, and touches every adapter/serializer test. Justified only after the benchmark proves OLMoCR value.
Option 3 — separate DocumentResult: a new value type (pages[], markdown, spans, assets) for document-understanding engines. Most invasive: new contract surface, new converters, consumer migration. Deferred — there is exactly one candidate producer today; introducing a second result taxonomy for one producer violates the minimal-change discipline.
Compatibility check against all four result sites: contract B consumers read text/confidence/engine/word_count — all present (word_count = len(segments) is derived, not stored, per result.py:185-188); contract C consumers read text/bbox/engine_name/metadata — compatible (bbox may be None per page-level segments; OLMoCR emits no confidence → confidence=None is contract-legal, recorded in provenance.confidence_source as engine-reported-none); contract A is a storage ORM mapping into metadata. Existing engine="none" semantics are untouched. The critical rule for the owner’s question 10 (never lose Markdown structure) is therefore procedural: OLMoCR output must be stored verbatim as validated Markdown and never flattened into .text alone; .text may carry the same content for legacy consumers, but structure (headings, HTML tables, LaTeX, figure placeholders, lists) lives in the markdown representation plus per-page segments, and downstream consumers that need plain text derive it themselves outside the OCR core (P6 separation).

9. Benchmark Requirements (Gate Before Any Integration)
No capability claim about OLMoCR may graduate from PARTIALLY PROVEN/UNPROVEN without a measured benchmark on owner-approved data. The benchmark design reuses the Phase-1 D4 discipline (manifest schema F11/E.2, PHI-free corpus, owner-gated corpus inputs, frozen corpus, characterization-vs-E2E separation) and adds OLMoCR as a fourth engine through the W6 benchmark wrapper (packages/benchmark_core/benchmarks/ocr/olmocr.py, mirroring the existing benchmark_image → {text, num_blocks, avg/min/max confidence, latency} pattern).
Corpus (20–50 pages, owner-approved before acquisition): Arabic printed text; Arabic medical text; English medical text; Arabic-English mixed lines (e.g. “Open reduction and internal fixation (ORIF)”); native tables; mathematical/equation content; multi-column pages; clean scanned pages; poor-quality scans; handwriting samples. Existing repo assets (training-data/samples, medical-ocr-benchmarks data, scanner-fixer verification scans) are candidates but the D4 corpus grant remains owner-gated and was NOT frozen in Phase 1.
Text metrics: CER and WER per engine per category (packages/benchmark_core already implements CER/WER decomposition in benchmarks/ocr/*.py run() outputs).
Structure metrics: heading preservation, paragraph order, table row/column/cell-relationship preservation (table_parsing style checks), equation validity (LaTeX parse), column ordering (full-column-1-then-column-2, never interleaved lines), markdown round-trip validity.
Arabic-specific metrics: Arabic character accuracy, RTL ordering correctness, diacritics handling, Arabic medical terminology retention (orthopedic/clinical terms bilingual), mixed-direction line integrity.
Operational metrics: runtime/page, host RAM, GPU VRAM, CPU, disk, failure rate (fallback-page rate upstream equivalent), cold-start model load time; measured on the same host for all engines where applicable; OLMoCR numbers require a GPU host (section 10).
Decision rule fixed in advance: OLMoCR may become a document-engine candidate only if it beats the existing ensemble on structure metrics for English categories AND does not fail catastrophically on Arabic categories; otherwise it is NO-GO regardless of layout brilliance (owner instruction 42: layout strength alone suggests hybrid division of labor, not replacement).

12. Security Review (Audit Only — No Changes Now)
Reviewed against the owner’s checklist: malicious PDF, subprocess, shell injection, path traversal, temporary files, unsafe deserialization, model loading, network access, untrusted artifacts. Findings, none of which were acted upon:
Subprocess surface (PROVEN, upstream): renderpdf.py invokes pdfinfo and pdftoppm in list-form subprocess (no shell=True) with a 120 s timeout per page; pipeline.py spawns vllm serve via asyncio.create_subprocess_exec. Untrusted PDFs are parsed by poppler (C++) — the same trust boundary tesseract already has in this repo — but poppler’s CVE history means the OLMoCR worker should run in a container with limited egress, as the repo’s Docker pattern already does for other engines.
No shell injection vector found in upstream (no shell=True in the inspected paths). Path traversal: get_markdown_path (pipeline.py:654-694) explicitly strips ‘..’ components and forces outputs under workspace/markdown/ — defense present, though symlink handling is not addressed; our adapter would keep the same containment rule (input path must never control output outside a temp workspace).
Temporary files: process_single_pdf downloads to a temp file and unlinks in finally (pipeline.py:588-599); acceptable, but our adapter must add size/page-count caps — upstream has NO decompression-bomb guard (a 10,000-page PDF would render 10,000 pages unless the error-rate discard triggers); this is an adapter-time responsibility (max_pages/timeout config proposed in section 4).
Unsafe deserialization: none found — no pickle usage in the inference path; model loading is safetensors via HF/vLLM. Model artifacts must be pinned: adapter config fixes model id (allenai/olmOCR-2-7B-1025-FP8) and should verify the HF revision hash before load (untrusted-artifact rule).
Network: local pipeline is offline after model download (PROVEN); S3 coordination, --server endpoints and provider API keys are opt-in paths. In this repository any remote mode must pass the canonical CloudGate protocol (fail-closed, explicit opt-in, PHI policy check) — the same two-state contract D3 delivered. Standing rule re-affirmed: LOCAL OCR FAILURE ≠ PERMISSION TO UPLOAD PHI; any public HF upload containing OCR data is a security finding (v1.2.2 §7/28).
vLLM server binding: vllm_server_task serves on args.port (default from CLI) — on a shared host it must bind localhost only; that is configuration hygiene for the implementation phase, recorded here, not changed now.

16. Risks
Arabic capability (TOP RISK): every Arabic row is UNPROVEN; if the benchmark fails Arabic categories, OLMoCR’s role collapses to English-layout-only or nothing. Mitigation: benchmark gate before any integration decision.
Dependency conflict (PROVEN, concrete): the repo pins transformers&gt;=5.10,&lt;5.13 across 4 requirements files (TASK-02D remediation, with TrOCR compatibility bound found by binary search), while olmocr[gpu] pins transformers==4.57.3 and vllm==0.11.2. GPU operations burden: ≥12 GB VRAM + ≈30 GB disk per worker; no GPU exists in CI today; procurement/rental decision is owner-side.
Upstream cadence and drift: vLLM/transformers pins move fast upstream (v0.4.x releases Jan–Mar 2026); doc drift already observed inside upstream (README --model help text says olmOCR-7B-0725-FP8 while pipeline.py:1213-1214 defaults to olmOCR-2-7B-1025-FP8 — code wins). Dead-abstraction risk (Vyce-noted in Phase 1): registering OLMoCR in the registry/router without any production caller could add another unwired stub (like QARI/Nougat/Qwen today). Mitigation: benchmark-first integration proves value before wiring; registry entry only makes it probeable.
Scope creep: OLMoCR brings a pipeline toolkit (S3, Beaker, filters) that must NOT be adopted wholesale; only the model-inference path is relevant. The adapter must wrap the model call, not import the fleet tooling.
Privacy/licensing of inputs: books may be copyrighted/proprietary; external API modes are opt-in only; local execution is the default (v1.2.2 §27).
